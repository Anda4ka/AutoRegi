# webapp — Telegram Mini App

Пять вкладок: **Проекты** (список, запуск, экспорт своих регистраций в буфер —
`api/results`), **Конструктор** (2026-09-10, см. ниже), **Очередь** (что идёт,
недавние, ошибки, плюс личная история за 7/30 дней — `api/stats`, грузится по
тапу и кэшируется 2 минуты, поллинг состояния её не трогает), **Минты**
(календарь; рисуется только пока `state.mints.enabled` — обе ветки API обязаны
отвечать `enabled: true/false`, иначе вкладка исчезает в обоих состояниях),
**Настройки** (была «Моё», переименована 2026-09-10: аккаунты — включая
удаление одной строки по номеру через `api/data/delete_row`, сам список
кошельков в браузер не уходит; прокси + здоровье за 24 ч; тариф, язык,
тумблер напоминаний о минтах).

Начиналось как отдельный процесс с базой только на чтение. Сейчас сервер живёт
**потоком внутри процесса бота** — иначе нельзя: очередь лежит в памяти этого
процесса, и задача, вставленная откуда-то ещё, это строка, которую никто не
возьмёт. Подробности и вся цепочка рассуждений — в `webapp/actions.py`.

```
webapp/auth.py       проверка initData — первая граница
webapp/actions.py    что мини-аппу вообще позволено; база отказывает во всём
webapp/state.py      выборка очереди одного пользователя (mode=ro)
webapp/ratelimit.py  три окна: по IP, по пользователю, отдельно на действия
webapp/server.py     http.server: страница + JSON-роуты
webapp/index.html    экран
tests/test_webapp.py, tests/test_webapp_actions.py
```

## Запуск

Обычно — сам, вместе с ботом: `WEBAPP_URL` задан → `tgbot.main` поднимает поток
и ставит ссылку на кнопку у поля ввода. Отдельно запускать **не нужно и вредно**:

```bash
python webapp/server.py --port 8081     # только посмотреть вёрстку
```

Так он поднимается в режиме «только просмотр» (`ReadOnly`) и, если бот уже
работает, займёт 8081 — мини-апп станет внешне исправным без единой работающей
кнопки.

Проверить без Telegram нельзя, и это правильно: страница требует `initData`,
которую подписывает клиент. Тесты подписывают её токеном бота и убеждаются, что
подделка получает `401`, чужая подпись ничего не меняет, а действия расходуют
собственное окно лимита.

## Безопасность

`initData` — единственное доказательство того, кто спрашивает. Страница живёт
на телефоне пользователя, поэтому user_id из запроса не берётся **никогда**:
он приходит только из `webapp.auth.user_id_from`.

Что проверяется и чем закрыто тестами:

| Проверка | Зачем |
|---|---|
| HMAC по схеме Telegram | подделанный хеш не проходит |
| подпись именно нашим токеном | чужой бот не подпишет за наш |
| правка `user` после подписи | главная атака: сохранить подпись, подменить чей это |
| `auth_date` не старше суток | подпись сама по себе не протухает, утёкшая строка иначе была бы вечным ключом |
| одинаковый текст любой ошибки | зонд не должен узнать, что именно не сошлось |
| нет токена → отказ | сервер без токена отказывает, а не «пропускает» |

`initData` уходит в теле POST, а не в query string: query-строки оседают в
логах доступа и истории браузера, а это учётные данные.

## Запуск из веба (2026-08-17)

Сервер больше не отдельный процесс. Он живёт **потоком внутри процесса бота**
(`tgbot.start_webapp`), и это не вопрос вкуса: очередь лежит в памяти этого
процесса (`bot/submit_queue.py`: `_queue`, `_jobs`), воркеры читают только
оттуда. Строка в `submit_jobs`, вставленная кем-то ещё, — это задача, которую
никто не подхватит.

Что из этого следует для эксплуатации:

* `webapp.service` больше нет — ни в `ops/`, ни в systemd (удалён 18.08.2026).
  Пока он лежал выключенным, единственной инструкцией к нему было «не
  запускать»: поднятый рядом с ботом, он занимал порт 8081, и мини-апп молча
  переходил в режим «только просмотр» — внешне исправно, но ни одна кнопка не
  срабатывала, потому что очередь живёт в памяти процесса бота. Юнит, который
  нельзя запускать, — это не артефакт деплоя, а ловушка.
* Туннель (`cloudflared-webapp.service`) не менялся: тот же 127.0.0.1:8081.
* Перезапуск бота теперь перезапускает и веб.

Права: `WEBAPP_WRITE_USERS` — список id через запятую или `*`. Пусто = только
`ADMIN_IDS`. `WEBAPP_ENABLE_ACTIONS=0` отключает запись целиком, оставляя экран.

## Данные и прокси из веба (2026-08-17)

Загрузка идёт **сырым телом**, а подпись — заголовком `X-Init-Data`. Причина в
порядке проверок: положи `initData` внутрь JSON — и полмегабайта тела придётся
прочитать целиком прежде, чем подпись внутри скажет, кто это вообще. С
заголовком проверяются подпись, окно по пользователю, бюджет действий и право
записи, и только потом сокет отдаёт файл.

Потолок тела для этих двух маршрутов свой (`_upload_cap()` — из
`USER_DATA_MAX_BYTES` / `USER_PROXY_MAX_BYTES`), остальные остаются на 16 КБ,
чтобы поток запросов не мог выпросить мегабайт, сменив путь.

Парсер один и тот же, что у .txt в чате (`save_user_data_from_bytes`,
`save_user_proxies_from_bytes`), поэтому строка, которую бот не принимает, не
проходит и здесь. Загрузка **заменяет** файл целиком — так же, как /data.

Проверено на живом 2026-08-17 (тестовые файлы, с бэкапом до начала):

| Что | Результат |
|---|---|
| Мусорный файл | `rejected`, построчные ошибки, файл на диске не тронут |
| Маленький файл | сохранён, экран сразу показал 3 |
| Очистка | 0 строк, проекты тут же ответили `no_data` |
| Полный файл 695 строк / 36 КБ | сохранён, побайтово совпал с исходным |
| Повторная загрузка 600 прокси | сохранено, файл идентичен |
| Чужой пользователь | `read_only` и на загрузку, и на очистку |
| Без заголовка с подписью | 401 |

## Тарифы, язык, отчёты (2026-08-17)

Третий слой закрывает остаток пользовательских кнопок. `admin:*` в вебе нет
намеренно: бан, рассылка, setvip и reload — самые опасные кнопки бота, а
вебвью — самая новая поверхность.

**Деньги.** Веб не решает, кому что зачислить. `/api/buy` просит у NOWPayments
адрес; зачисление делает `payments_poll.handle_status` по ответу самого
провайдера, и это тот же код, что у кнопки в чате и у фонового поллера.
Поэтому `/api/pay/check` безопасен: кто спросил — не влияет на ответ. Все
ограничители переиспользованы: `pay_create` 5/час, `pay_check` 6/мин, один
открытый счёт на пользователя, выключатель магазина и выключатель продаж.
Адрес и сумма уходят в вебвью строкой без форматирования — их копируют в
кошелёк, и укороченный адрес отправляет деньги в никуда.

**Язык** — единственное действие вне `may_write`: он меняет то, что читает сам
пользователь, и ничего больше.

**Отчёт об ошибках** отдаётся целиком (до 500 строк). Постраничность в чате
существует из-за лимита размера сообщения; у страницы его нет.

Заодно закрыт разрыв, оставшийся от второго слоя: загрузки из веба теперь
проходят через те же часовые лимиты, что и в чате (`bulk_file` 5/час,
`proxy_file` 10/час). Своё окно у веба поминутное и про час ничего не знает.

Проверено на живом 2026-08-17:

| Что | Результат |
|---|---|
| Каталог тарифов | basic $2, pro $10; продажи закрыты — так и показано |
| Покупка при закрытых продажах | отказ `closed`, счёт **не создан** |
| Чужой на `/api/buy`, `/pay/check`, `/pay/cancel` | `read_only` |
| Чужой счёт | `unknown`, один и тот же текст для «нет» и «не ваш» |
| Язык туда и обратно | ok, экран переключился; `fr` отвергнут |
| Реферальная ссылка | сохранена, прочитана из базы, прежнее значение возвращено |
| Несуществующий проект / короткое предложение | `unknown` / `too_short` |

**Не проверено на живом и почему:** создание счёта — продажи закрыты, а
открывать магазин ради теста я не стал; доставка ключей — сейчас ни у одного
проекта нет `queue_redeliver`.

## Аудит 2026-08-17

**Стоимость экрана.** Один опрос стоил **410 мс** процессора и повторялся каждые
4 секунды на каждого открытого экрана — десять человек заняли бы ядро целиком,
и заняли бы его внутри процесса бота, отбирая время у воркеров. Две причины:

* `caps()` пересчитывал через `batch_eligible_projects` ровно то, что уже
  посчитал `projects()` — 198 мс на второй проход. Теперь список передаётся.
* `has_user_data` и `count_user_data` парсят файл целиком, а спрашивают их по
  разу на проект: файл на 695 строк разбирался 42 раза за один опрос. В
  `bot/user_data.py` добавлен кеш, ключ — `(mtime_ns, size)` файла, так что
  устареть он может только вместе с самим файлом. Бот от этого выигрывает тоже:
  клавиатура на 16 кнопок делала 16 таких разборов.

Сейчас: **69 мс** на origin, 12.9 КБ ответа.

**Зависание потока.** У сокета не было срока: клиент, объявивший
`Content-Length` больше отправленного, держал бы поток вечно — а потоки живут
внутри бота. Проверено: до правки ответа нет вовсе, после — соединение
закрывается через 30 с и поток возвращается.

**Лимит на пользователя** был 40/мин при 15 запросах с экрана. Третий открытый
экран одного и того же человека начинал получать 429 от самого себя. Поднято до
120 — восемь экранов. Бюджет действий (12/мин) не тронут: защищает очередь
именно он.

**Враждебный ввод** по всем маршрутам (не JSON, массив вместо объекта, `job_id`
списком и в 10⁶⁰, `lang` числом, 5000-значное предложение, обход пути, файл в
UTF-16, нулевой байт, вложенность на 400 уровней): ни одной пятисотки, ни
зависаний, ни утечки потоков.

**Две давние падавшие проверки** починены. Причина у обеих одна: тестовые модули
чистят `bot.*` из `sys.modules`, и ссылки, захваченные при импорте, начинают
указывать на прежний экземпляр — грант VIP уходил в никуда, а сравнение
реестров сравнивало разные поколения. В продакшене этого нет: `/reload` чистит
только `projects.*`. Тесты переписаны так, чтобы брать модули из `sys.modules` в
момент вызова. (С 2026-09-09 purge-циклы чистят и `handlers.*` — рядом с `bot.*`.)

`ruff --select F,E9,B` по всему дереву: чисто. Шесть S608 проверены поимённо —
плейсхолдеры `?` и имена колонок из констант, пользовательский ввод туда не
попадает.

## Календарь минтов (2026-08-17)

Четвёртая вкладка. Данные — в `project_mints` / `mint_phases`, находки от
сборщика — в `mint_proposals`, и только принятое переходит в первые две.

Почему так, а не «модель пишет сразу»: два эндпоинта, которых спрашивали про
минты без исходного текста, отвечали уверенно и ссылались на страницы, которых
не открывали. Один из них дважды подряд выдал одни и те же неверные числа —
это читается как подтверждение, а не как сбой.

**Проверка цитаты.** Модель не спрашивают, что она знает. Ей дают один пост и
требуют вернуть подстроку, в которой она прочла ответ; код сверяет эту строку с
текстом. Не сошлось — находка выброшена до того, как её увидит человек.

**Чего проверка цитаты не ловит.** Цитата бывает подлинной, а прочтение
неверным: «18 авг» превратилось в 2024-08-18, потому что модель не знает
сегодняшнего числа. Теперь дата передаётся в каждый запрос, а результат старше
двух недель отбрасывается как угаданный год.

**Молчание сломанного провайдера — не факт.** `_ask` бросает `ExtractionDown`,
непрочитанные посты не помечаются прочитанными, `/scan_mints` называет
непрочитанные проекты отдельно. Это стоило один неверный вывод: обход упёрся в
месячный лимит ключа, все вызовы упали, отчёт сказал «находок 0» — и я прочитал
это как «проект ничего не объявлял».

**Цена.** X теперь по факту, без подписки и минимума: $0.01 за разрешение
логина (однократно навсегда), $0.005 за пост. Каждый запрос идёт с `since_id`,
поэтому проверка без новых постов бесплатна — частота опроса на счёт почти не
влияет.

## Тишина после тапа (2026-09-10)

Успешное действие из веба больше **не показывает никаких попапов** — ни
длинную карточку задания (`format_job_status` + заметка дедупа), ни
однострочный тост «Запущено». `act()`/`upload()` молчат при `ok=true`:
подтверждением служит сам экран (карточка проекта переключается на «идёт»,
бейдж «Очереди» тикает, список перерисовывается), а слова — только у отказа
(`ok=false`: нет слотов, нет данных, форма требует вход), потому что там
важно прочитать причину. Причина прежней боли: `act()` прогонял любой
`res.message` через `tg.showAlert`, и ответ кнопки «Старт» (весь статус
задания) открывался тёмным нативным окном после каждого тапа.

## Конструктор Google-форм (2026-09-10)

Вкладка «✚ Конструктор». Пользователь вставляет ссылку на публичную
Google-форму, сервер парсит `FB_PUBLIC_LOAD_DATA_` (`bot/gform.py`) и
показывает каждое поле `entry.*` с выбором источника:
`wallet / handle / quote_url / comment_url / option:<вариант> / static:<текст>
/ skip`. «Создать проект из формы» пишет адаптер в `~/.autoreg/user_projects/`
(реестр сканирует этот каталог вместе с `projects/`).

Структура `FB_PUBLIC_LOAD_DATA_` измерена на живой форме (2026-09-10):
`data[1][1]` — вопросы вида `[poster, title, null, type, [[entry, options,
required], …], …]`, имя поля POST — `entry.<entry>`. Первый вариант парсера
искал entry-ids в `question[0]` и на любой реальной форме падал `TypeError`
→ 500 «сервер не отвечает»; фикстура тестов теперь строит измеренную
структуру, чтобы это не вернулось.

Правила (2026-09-10):

* **1 форма = 1 проект со своим лимитом тира**; `MAX_USER_FORMS` (10) —
  сколько форм один пользователь может держать.
* **Видна только создателю** (`only_user_ids`); работает у него сразу, по его
  тиру, через обычные ворота очереди. Админам уходит DM «✅ Показать всем /
  ✖️ Только ему» (`gform:pub/no:<id>`) — публикация только снимает пин.
* Отказы на этапе парсинга: форма требует вход в Google (`401` на
  `formResponse`), закрыта, капча. Кулдаун «Распарсить» — 30 с на человека
  (это исходящий GET); распарсенная форма живёт на сервере 10 минут —
  «Создать» не фетчит заново и не верит копии полей из браузера.
* `wallet` обязан быть назначен хоть одному полю, каждое обязательное поле —
  иметь источник: без кошелька нет ни дедупа, ни счётчика слотов.
* Удаление — только создателем, отменяет задания проекта, история
  регистраций в БД остаётся. Повторное добавление той же формы даёт тот же
  детерминированный id (`gf<sha1[:8] из uid:form_id>`).
* Чат-команда `/gform <url>` (админ) — тот же движок, но черновик уходит в
  `projects/` классическим отключённым адаптером.
* Экран маппинга берёт у пользователя **название проекта** (по умолчанию —
  заголовок формы; «Free Mint» у тысячи форм — не имя) и **ссылку на X или
  сайт**: x.com/twitter становится кнопкой «🐦 X», другая http(s) — «🌐 Сайт»,
  мусор отбрасывается, а URL самой формы никогда не выдаётся за сайт проекта.

Маршруты: `api/gform/parse`, `api/gform/create`, `api/gform/delete`.
Тесты: `tests/test_gform.py`.
