# Публикация Mini App через Cloudflare Tunnel

Хост за NAT: наружу открыт только 22-й порт, локальный адрес `10.0.0.10`,
внешний — другой. Открывать 80/443 пришлось бы в панели облака и подставлять
машину под сканеры. Cloudflare Tunnel этого не требует: соединение исходящее,
входящих портов ноль, сертификат и TLS на стороне Cloudflare.

```
Telegram ──https──> Cloudflare edge ──туннель (исходящий)──> cloudflared ──> 127.0.0.1:8081
```

---

## Что нужно от вас — и чего присылать НЕ надо

**Не вставляйте в конфиги API-токены, ключи и пароли от Cloudflare.** Они
здесь не нужны: вход делается в браузере и кладёт сертификат прямо на
сервер. Всё, что нужно задать руками, — **имя поддомена**,
например `app.example.com`.

### Шаг 1 — вход в Cloudflare (один раз)

```
cloudflared tunnel login
```

Команда напечатает ссылку. Откройте её в браузере, выберите нужный домен и
подтвердите. После этого на сервере появится `~/.cloudflared/cert.pem` — это и
есть доступ, дальше всё делается им.

### Шаг 2 — задайте поддомен

Имя поддомена из шага выше, например `app.example.com`, идёт в конфиг
туннеля и в DNS-запись ниже.

---

## Пример развёртывания

Туннель `autoreg-webapp`, хост `app.example.com`, четыре соединения до
edge (sin14/sin18/sin21, QUIC). Сервисы `webapp` и `cloudflared-webapp` в
автозапуске. Проверено снаружи: страница `200` с валидным TLS, подделанная
`initData` — `401`, любой другой путь — `404`.

Кнопка «🚀 Открыть приложение» появляется в списке проектов, когда задан
`WEBAPP_URL`, и та же ссылка ставится на кнопку у поля ввода (`set_menu_button`
при старте бота). Пусто — ни того, ни другого, и бот ровно такой, каким был.

Главное мини-приложение (`t.me/<bot>/app`, кнопка в профиле) настраивается
только в BotFather: Bot Settings → Configure Mini App. В Bot API метода нет.

## Команды, которыми это сделано

```bash
cloudflared tunnel create autoreg-webapp          # создаёт туннель + credentials json
cloudflared tunnel route dns autoreg-webapp app.example.com   # CNAME в вашей зоне
sudo cp ops/cloudflared.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now cloudflared-webapp

# Отдельного webapp.service нет и заводить его не нужно: с 2026-08-17 сервер
# живёт внутри процесса бота (очередь в его памяти), а сам юнит удалён
# 18.08.2026. Поднятый отдельно, он занимал 8081 и мини-апп становился
# «только просмотр» — внешне исправным, но без единой работающей кнопки.
```

Конфиг туннеля (`ops/cloudflared-config.yml`, подставляется имя):

```yaml
tunnel: autoreg-webapp
credentials-file: /etc/cloudflared/<tunnel-id>.json
ingress:
  - hostname: app.example.com
    service: http://127.0.0.1:8081
  - service: http_status:404          # всё остальное закрыто
```

Последнее правило обязательно: без него туннель проксирует что угодно, а так
наружу торчит ровно один хост и ровно один порт.

### Шаг 3 — кнопка в боте

После того как адрес открывается, в `tgbot.py` добавляется одна кнопка:

```python
types.InlineKeyboardButton("📊 Очередь", web_app=types.WebAppInfo(url=WEBAPP_URL))
```

Это единственная правка бота во всей затее, и она обратима: убрать кнопку —
значит вернуться ровно к тому, что работает сейчас.

## Что проверить после запуска

```bash
systemctl status webapp cloudflared-webapp
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/     # 200 локально
curl -s -o /dev/null -w '%{http_code}\n' https://app.example.com/    # 200 снаружи
```

Открывать `https://app.example.com` в обычном браузере бесполезно и это
правильно: без `initData` от клиента Telegram страница честно скажет, что
подтвердить сессию нечем. Проверять — только кнопкой из бота.

## Ограничение частоты

Сделано **на origin**, в `webapp/ratelimit.py`, и работает независимо от того,
что настроено в панели Cloudflare: правило на edge можно случайно снести в
дашборде, о котором этот процесс ничего не знает, а сервер не должен зависеть
от контроля, которого не видит.

| Окно | Порог | Зачем |
|---|---|---|
| по IP клиента, **до** проверки подписи | 60/мин | неаутентифицированный флуд — то, на что напрашивается открытый хост; отсекается до HMAC |
| по Telegram-пользователю, **после** проверки | 40/мин | живая страница опрашивает раз в 4 с; заметно чаще — это баг либо переигранная `initData` |

Адрес клиента берётся из `CF-Connecting-IP`. Доверять заголовку обычно нельзя,
и здесь это корректно **только потому**, что сервер слушает `127.0.0.1` и
единственный путь к нему — туннель на той же машине. Изменится это — придётся
менять и допущение.

Проверено через туннель: из 65 запросов подряд 60 дошли до проверки подписи
(`401`), 5 отсечены (`429`), страница при этом продолжает отдаваться.

**Порог по IP намеренно щедрый.** Первая версия ставила 60/мин, и это была
ошибка: при опросе раз в 4 секунды (≈15 запросов/мин на страницу) за одним
адресом помещалось всего четыре клиента, а мобильные операторы держат за одним
CGNAT-адресом тысячи абонентов. Такое правило било бы по своим же
пользователям. Ограничение по IP нужно только чтобы ограничить флуд —
проверка подписи занимает микросекунды, а до базы неаутентифицированный запрос
не доходит вовсе, — поэтому 300/мин свою задачу решает и оставляет место
двадцати телефонам на одном адресе. Настоящий предел — по пользователю: он
привязан к проверенному Telegram-id, и NAT там ничего не смешивает.

Те же цифры стоит повторить на edge — см. правила ниже.

## Cloudflare Access сюда не подходит

Раньше я написал, что Access можно включить «без правок кода». Формально да,
но **приложение от этого перестанет работать**, и вот почему.

Access — это гейт по личности: посетителя без валидного Access-JWT
перебрасывает на страницу входа. Mini App открывается **во встроенном браузере
самого пользователя**, а не на серверах Telegram. То есть в Access упрётся не
Telegram, а каждый ваш пользователь, и увидит он форму входа Cloudflare вместо
очереди. Отфильтровать «только Telegram» по IP тоже нельзя по той же причине:
запросы идут с телефонов людей, а не из дата-центра Telegram.

Access остаётся уместным, если однажды появится админский экран для двух-трёх
человек — вот его закрывать им правильно.

Настоящая защита этого адреса — не сетевая, а подпись: без `initData`,
подписанной токеном бота, `/api/state` отвечает `401`, и никакие данные наружу
не уходят. Сама страница статична и ничего не раскрывает. Поверх этого стоит
ограничение частоты выше.

## Правила на edge: что нажимать

Три правила. Первое — реально полезное, остальные два просто отсекают мусор
до origin. Выражения лучше вставлять через **Edit expression** (кнопка справа
над конструктором): текст правила от перестановок в интерфейсе не зависит.

### 1. Ограничение частоты на `/api/state`

**Dashboard → домен `example.com` → Security → WAF → вкладка
Rate limiting rules → Create rule**

На бесплатном тарифе форма урезана: период фиксирован **10 секунд**, timeout
тоже 10, и правило этого типа доступно одно. Это нормально — считать надо не в
минутах, а в десятках секунд.

| Поле в форме | Что ставить |
|---|---|
| Rule name | `webapp api state` |
| When incoming requests match | **нажать `Edit expression`** и вставить строку ниже |
| With the same characteristics | `IP` |
| When rate exceeds | `300` requests per `10` seconds |
| Then take action | `Block` |
| For duration | `10` seconds |
| Status | `Active` |

```
(http.host eq "app.example.com" and http.request.uri.path eq "/api/state")
```

**Конструктор оставлять нельзя.** По умолчанию он показывает
`(http.request.uri.path wildcard r"")` — пустой шаблон, который совпадает не с
тем, с чем нужно, а само правило тогда считает трафик всей зоны, включая другие
поддомены. Только `Edit expression` и вставка целиком.

Если редактор откажется принимать `http.host` (на бесплатном тарифе набор полей
урезан), оставьте одну проверку пути:

```
(http.request.uri.path eq "/api/state")
```

Такого роута нет больше нигде в зоне, так что правило всё равно попадёт только
в приложение.

**Про цифры.** 300 за 10 секунд — это внешняя граница против волюметрики, а не
политика. Настоящий предел живёт на origin: 300/мин по IP и 40/мин по
проверенному пользователю. Такое разделение сознательное: edge отбивает поток,
origin решает, что честно. Ставить на edge что-то узкое опасно ровно по той же
причине, по которой пришлось поднимать порог на origin — за одним CGNAT-адресом
оператора сидят тысячи абонентов, и страница каждого опрашивает раз в 4 секунды
(≈2.5 запроса за 10 секунд). Порог 300 оставляет место сотне телефонов на одном
адресе.

### Проверить, что правило вообще живое

Задеплоить мало: молчащее правило снаружи неотличимо от узкого. Пустой шаблон
`wildcard r""` не совпадает ни с чем, выключенный статус — тоже, и в обоих
случаях сайт работает как ни в чём не бывало.

Проверка — устойчивая перегрузка, а не короткий всплеск: окно 10 секунд, и
пачка, которая закончилась за 4 секунды, законно проскакивает.

```bash
# держать выше порога несколько окон подряд
python - <<'EOF'
import concurrent.futures as cf, time, requests
from collections import Counter
def hit(_): 
    try: return requests.post("https://app.example.com/api/state",
                              json={"initData":"x"}, timeout=15)
    except Exception: return None
def kind(r):
    if r is None: return "error"
    if r.status_code == 403 and "cloudflare" in (r.headers.get("Server") or "").lower():
        return "403 EDGE"
    return str(r.status_code)
t0 = time.time(); total = Counter()
with cf.ThreadPoolExecutor(max_workers=60) as pool:
    while time.time() - t0 < 45:
        total.update(kind(r) for r in pool.map(hit, range(45)))
        time.sleep(0.3)
print(dict(total))
EOF
```

**Считать по коду ответа нельзя, и на этом я один раз уже ошибся.** Cloudflare
отдаёт блок rate limiting как **`429`** — тем же кодом, которым отвечает наш
собственный лимитер. Заголовок `server: cloudflare` стоит на всех ответах и
тоже не разделяет. Первая версия проверки складывала любые `429` в «origin» и
объявила рабочее правило молчащим; блоки всё это время лежали в
**Security → Events**.

Различает только тело: origin отвечает ровно
`{"error": "rate limited"}` с `Content-Type: application/json`, Cloudflare —
своей HTML-страницей.

```python
def kind(r):
    if r.status_code != 429:
        return str(r.status_code)
    ctype = (r.headers.get("Content-Type") or "").lower()
    if "application/json" in ctype and "rate limited" in (r.text or ""):
        return "429 ORIGIN"
    return "429 EDGE"
```

Если после этого `429 EDGE` всё равно ноль — тогда смотреть три вещи:

1. **Expression.** Открыть правило → `Edit expression` и убедиться, что там
   полная строка, а не `(http.request.uri.path wildcard r"")` из конструктора.
2. **Status.** Переключатель `Disabled / Active` — должен стоять `Active`.
3. **Security → Events**, фильтр `Action = Block`. Если правило срабатывало
   хоть раз, оно там будет; пусто — значит не совпадает.

### Итог проверки 17.08.2026

Правило работает. Под устойчивой нагрузкой ответы приходят как
`429` с `Content-Type: text/html` — это страница Cloudflare, то есть запросы
до origin уже не доходят. После снятия нагрузки приложение доступно сразу:
подписанная `initData` снова отдаёт очередь, страница — `200`.

Два замера до этого объявляли правило молчащим. Оба были неверны, и по одной
причине: классификатор считал любой `429` ответом origin. Из этого стоит
запомнить не «Cloudflare отдаёт 429» (это деталь), а то, что **сходство кодов
ответа у двух разных слоёв делает измерение бесполезным, пока их не научишься
различать по телу.** Ошибка выглядела как отчёт об отказе чужой системы —
самый неудобный вид ошибки, потому что заставляет чинить исправное.

Оба слоя на месте и делают разное: edge снимает объём, origin решает, что
честно, и продолжает работать, даже если правило в панели выключат.

### 2. На `/api/state` только POST

**Security → WAF → вкладка Custom rules → Create rule**

Если вкладки Custom rules не видно: в новом дашборде раздел переехал в
**Security → Security rules**, а старый путь остался как
**Security → WAF → Custom rules**. На бесплатном тарифе таких правил даёт пять,
нам нужно максимум два.

| Поле | Значение |
|---|---|
| Rule name | `webapp api post only` |
| Expression | ниже |
| Action | `Block` |

```
(http.host eq "app.example.com" and http.request.uri.path eq "/api/state"
 and http.request.method ne "POST")
```

Предзапросов CORS здесь не бывает: страница и роут на одном источнике, браузер
`OPTIONS` не шлёт. То есть правило ничего живого не задевает.

### 3. Только известные пути

**Там же → Create rule**

| Поле | Значение |
|---|---|
| Rule name | `webapp known paths` |
| Expression | ниже |
| Action | `Block` |

```
(http.host eq "app.example.com"
 and not http.request.uri.path in {"/" "/index.html" "/api/state"})
```

Туннель и так отвечает `404` на всё прочее — это правило просто не пускает
сканеры дальше edge. **Учтите:** добавите когда-нибудь новый роут — его надо
будет дописать сюда, иначе он молча получит `Block`. Если такая ловушка не
нравится, это правило можно и не заводить: без него ничего не ломается.

### Проверить, что не сломали

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://app.example.com/          # 200
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  -H 'Content-Type: application/json' -d '{"initData":"x"}' \
  https://app.example.com/api/state                                        # 401
curl -s -o /dev/null -w '%{http_code}\n' https://app.example.com/api/state # 403 (правило 2)
curl -s -o /dev/null -w '%{http_code}\n' https://app.example.com/wp-admin  # 403 (правило 3)
```

И главное — открыть кнопку «🚀 Открыть приложение» в боте. Если очередь показывается,
правила настроены верно.

Заблокированное видно в **Security → Events**: там фильтр по Action = Block
покажет, что именно отсекается, если вдруг попадёт лишнее.
